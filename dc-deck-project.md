# dc-deck — автоматизация еженедельной презентации Дхармачакры

Документ описывает проект целиком: архитектуру, добавленный слайд «Уроки медитации», фичу ручного добавления новых Прабхат Самгитов через операторку, найденные и починенные баги, принятые принципы и открытый бэклог.

Дата составления: 22 августа 2026.

---

## 1. Что это за проект

**dc-deck** — система, которая автоматически собирает еженедельную презентацию для встречи Дхармачакры (Ростов) вместо ручной вёрстки в Google Slides.

Раз в неделю скрипт собирает данные из нескольких источников, печёт из них манифест, деплоит его на сервер, и дек показывается на проекторе через Reveal.js.

**Стек:** Python (сборка на Mac) + Reveal.js/FastAPI (показ) + Caddy + Postgres на VPS. Telethon для Telegram, Airtable как календарь событий, Groq как LLM-провайдер.

---

## 2. Архитектура: три слоя

Ключевое решение, вокруг которого построено всё остальное — данные приходят из трёх независимых слоёв, которые сливаются в браузере:

| Слой | Где живёт | Что содержит | Кто пишет |
|---|---|---|---|
| **manifest** | `data/manifest.json` → rsync на VPS | автоданные: программа, новости, деньги, видео, песни, слайд УМ | билд на Mac |
| **selection / overrides** | Postgres на VPS | ручные правки оператора | форма оператора |
| **theme** | `theme.json` в репозитории | константы оформления | разработчик |

Слияние происходит в `deck/merge.js` уже на клиенте.

### Почему сборка на Mac, а не на сервере

VPS находится в РФ, и с него **недоступны** Telegram, Airtable и Groq. Поэтому Mac работает как узел сбора данных: он ходит во внешние сервисы, собирает манифест и отправляет на сервер только готовый артефакт. VPS наружу не ходит вообще — рендерер читает статику.

### Единая точка LLM

LLM вызывается ровно в одном ограниченном месте, вокруг него — детерминированный код. Сырой вывод модели никогда не попадает на экран: он проходит валидатор и запекается в манифест готовой строкой.

## 3. Слайд «Уроки медитации» (основная работа этой сессии)

### Задача

Добавить опциональный слайд в конец дека — приветственный слайд проекта «Уроки медитации» (УМ), который появляется только в те недели, когда проходит коллективная медитация (КМ).

Цель слайда: поприветствовать, показать месяц целиком, дать QR для доната, закончить показ на спокойной ноте. Без цен.

### Триггер (эволюция)

Изначально задумывался тройной триггер: КМ в новостях **И** КМ в программе **И** воскресенье. В процессе факт-чека выяснилось, что это неверно.

**Ключевой инсайт:** в Airtable есть два разных «медитационных» события:

- **Дхармачакра (ДЧ)** — Тип `АМ`, всегда воскресенье. Главная встреча.
- **Коллективная медитация (КМ)** — Тип `УМ`, обычно суббота, редко воскресенье.

Проверка по программе оказалась ложным условием: программа/пост — про ДЧ, и КМ Уроков там может вообще не быть.

**Финальный триггер:**

```
append ⇔ в ISO-неделе даты ДЧ есть published-событие
         с kind == "km" (Тип УМ), чья МСК-дата = воскресенье
```

Суббота-КМ → слайда нет. Airtable — единственный источник истины.

### Фильтрация данных

В календарь слайда попадают **только события Тип УМ**. Всё с меткой `АМ` (Дхармачакра, Сатсанг, Садхана Шивир, Ремонт, Поход) отбрасывается на входе — слайд принадлежит проекту «Уроки медитации», чужие события на нём не место.

### Классификация событий (`kind`)

Готового поля-категории в Airtable нет (поле `Тип` — это направление УМ/АМ, а не категория), поэтому `kind` выводится из имени события по словарю в конфиге:

| kind | ключевые слова | цвет |
|---|---|---|
| `km` | коллективная медитац, км с дадой | сиреневый (герой) |
| `asana` | асан | оранжевый |
| `fk` | философск, фк | нейтральный |
| `charity` | кормлен, благотвор | светло-сиреневый |
| `other` | фолбэк | нейтральная ячейка |

Словарь вынесен в `build/urokimeditacii.json` — расширяется без правки кода.

**Важный принцип, выявленный в процессе:** классификация и триггер должны использовать **одну и ту же функцию**. Был баг, когда триггер сравнивал буквальную строку «Коллективная медитация», а классификатор работал по словарю — в результате событие «КМ с Дадой» красилось как КМ, но триггер его не видел.

### Источники данных слайда

| Что | Откуда |
|---|---|
| Календарь месяца | Airtable, фильтр Тип=УМ, парсинг без синтеза дней недели |
| Расписание встречи | **отдельный пост в канале УМ** (`t.me/urokimeditacii_rnd`), пост той же ISO-недели, что и КМ |
| Строка-напутствие (wisdom) | LLM (Groq → OpenRouter), единая точка |
| greeting, schedule_note, channel | константы конфига |

Расписание встречи берётся **не** из ДЧ-поста: это разные аудитории. ДЧ — для практикующих (там есть, например, Каошики-Тандава), пост УМ — публичный анонс для новичков (только КМ + чаепитие).

### Схема манифеста

```json
"urokimeditacii": {
  "month_label": "август 2026",
  "wisdom": "<валидированная строка>",
  "channel": "t.me/urokimeditacii_rnd",
  "highlight_day": 16,
  "meeting": {
    "date_label": "вс 16 августа",
    "items": [
      {"time": "11:00", "name": "Коллективная медитация", "km": true},
      {"time": "12:00", "name": "Чаепитие"}
    ]
  },
  "calendar": [
    {"day": 1, "kind": "km", "label": "КМ · киноклуб"},
    {"day": 4, "kind": "asana", "label": "Асана-класс"}
  ]
}
```

Ключ отсутствует → слайда нет. `meeting: null` → карточка расписания не рисуется, слайд цел.

### LLM-точка: строка-напутствие

Единственный вызов LLM во всей фиче. Работает только на Mac.

**Промпт (сокращённо):** одна короткая строка на русском для приветственного слайда встречи коллективной медитации. Не цитата, не молитва, не эзотерика — простая тёплая мысль про тишину, внимание, дыхание, присутствие. 6–14 слов, без кавычек, эмодзи, цифр, латиницы, имён, повелительных команд и пафоса.

**Детерминированная обёртка вокруг:**

- `temperature ≈ 0.8`, `seed = ISO-неделя`, `max_tokens ≤ 40`
- валидатор: 6–14 слов, ≤90 символов, ≤1 терминальный знак; reject на эмодзи / цифры / латиницу / кавычки / URL / маркеры списка / финальное тире
- дедуп по `wisdom_history.json` (последние ~8 недель)
- 3 попытки регенерации → фолбэк-пул из 10 строк, ротация по `iso_week % N`
- никогда не бросает; при отсутствии сети детерминированно берёт из пула

Проверено на 11 «злых» кейсах — все отклонены. Дедуп сработал живьём: повторный билд той же недели дал совпадение с историей → перегенерация.

### Дизайн слайда: путь от v1 до v14

Макет прошёл 14 итераций. Ключевые развороты:

1. **Светлая палитра, не тёмная.** Дек тёмный (`#0e1524`), слайд УМ — тёплый светлый (`#F4EEDE`), в стиле афиш проекта. Сознательное отличие: это сигнатурный слайд подпроекта. Все стили отскоуплены под `.um-slide`, чтобы светлое не протекло в тёмный дек (изоляция доказана рендером бок о бок).
2. **Вертикальный стек → две колонки.** Слева приветствие, расписание встречи, QR-донат; справа календарь месяца; внизу цитата во всю ширину.
3. **Убрана карточка «Сегодня»** — дублировала календарь и порождала путаницу «какой день считать сегодняшним» при заранее собираемом деке.
4. **Убрано гипер-выделение** дня встречи, легенда над календарём, kicker над «Намаскар».
5. **Крупный масштаб под проектор.** QR увеличен более чем вдвое (до 130px), расписание встречи до 21px, приветствие до 36px — на проекторе мелкое не читается и не сканируется.
6. **Компактные ячейки календаря.** Главная находка: `grid-auto-rows: 1fr` растягивал 5 рядов на всю высоту колонки → пять огромных пустых боксов, «много места, мало информации». Заменено на фиксированные `42px` + центрирование сетки в панели. Пустота стала спокойным полем, а не решёткой пустых клеток.

## 4. Баги, найденные и починенные по пути

Работа над слайдом вскрыла целый пласт проблем, не связанных с ним напрямую. Это оказалось ценнее самой фичи.

### 4.1. `manifest.date` никогда не обновлялась автоматически 🔴

**Симптом:** дек собирался на прошлое воскресенье, при этом сводка рапортовала «всё ✅».

**Причина:** билд перезаписывал только содержимое (`news`, `program`, `raised`, `video_url`, `urokimeditacii`), но **не якорную дату**. Дату двигали вручную перед прожигом. Забыли подвинуть — и весь дек собран на неделю назад, потому что всё содержимое считается от якоря.

**Починка:** дата вычисляется автоматически как ближайшее предстоящее воскресенье. Оставлена возможность явного override для пересборки прошлых недель. В сводку добавлен **жёсткий красный чек**: если итоговая дата ≠ ближайшему воскресенью → ❌ в самый верх, независимо от остального.

### 4.2. Оверрайды не протухали между неделями 🔴

**Симптом:** дек показывал новости прошлой недели, игнорируя свежие из Airtable.

**Причина:** `merge.js` устроен так, что `overrides.news` полностью перекрывает `manifest.news`. Механизм работал как задумано, но у оверрайда не было срока годности — оператор вписал новости неделю назад, и они висели вечно.

**Починка:** staleness guard — если `selection.week_date` не совпадает с ISO-неделей `manifest.date`, недельные оверрайды не применяются.

**Побочка и её исправление:** первая версия guard отбрасывала оверрайды целиком (`ov = {}`), из-за чего пропали «важные новости» оператора (анонс сентябрьского семинара), которые актуальны месяцами. Введена выборочность:

```js
const PERSISTENT_OVERRIDE_KEYS = ['featured_news', 'hide_urokimeditacii'];
```

Персистентные поля переживают смену недели, недельные — нет. Явный whitelist (а не хардкод одного поля), чтобы новые персистентные поля не протухали молча по забывчивости.

`hide_urokimeditacii` отнесён к персистентным осознанно: слайд появляется редко, и если сбросить тумблер, скрытый слайд молча вылезет на показ через несколько недель, когда оператор уже забудет, что скрывал.

### 4.3. Форма ломала механизм протухания 🔴

**Скрытый баг**, найденный при работе над песнями: форма оператора при сохранении **переиспользовала старый `week_date`**, поэтому staleness не срабатывал никогда. Весь механизм протухания был обесценен.

**Починка:** `week_date` при сохранении = `manifest.date`.

### 4.4. Песни не парсились вообще, систематически 🟡

**Симптом:** `songs=[]` во всех билдах подряд, при том что номера ПС регулярно пишут в чат.

**Диагностика по шагам** (регэксп, окно дат, ранний break, фильтр отправителя) выявила единственную причину:

`TELEGRAM_SENDER` был настроен на **канал** (`-1002499260992`). Программу и финансы публикует канал — они проходят фильтр. А номера ПС пишет **живой участник** (`543422193`) — фильтр резал его сообщение через `continue`, и парсер до текста просто не доходил.

Конфликт дизайна: один фильтр применялся к трём сущностям разной природы.

**Починка:** фильтр сделан избирательным. Программа и финансы — строго от канала (защита от случайных сообщений). Песни ищутся по всем постам в окне, независимо от отправителя. Ранний `break` расширен до `if program and finance and songs is not None`.

Обоснование широкого захвата: песни — это подсказка, а не источник истины, между ложным номером и экраном стоит человек.

### 4.5. Песни требовали ручного «Применить» каждую неделю 🟡

**Причина:** номера из чата попадали в `suggested_songs` и ждали подтверждения кнопкой.

**Починка:** инвертирован приоритет. Свежие номера из чата встают автоматически; оператор заходит только чтобы изменить.

| Состояние `selection.song_numbers` | Поведение |
|---|---|
| свежие (та же ISO-неделя) + непустые | ручной ввод главнее, автоматика не перезаписывает |
| протухшие или пустые + чат дал номера | применяются номера из чата автоматически |
| протухшие + чат пуст | остаются старые + ⚠️ в сводке (не обнуляем) |

### 4.6. Билд затирал программу при отсутствии поста 🟡

**Причина:** если пост ДЧ не найден (вышел из окна `TELEGRAM_HISTORY_DAYS=7`), билд обнулял `manifest["program"] = []`.

**Починка:** при «пост не найден» прежняя программа сохраняется + WARN, как уже делалось при обрыве Telethon. Сбой источника не должен уничтожать живые данные.

Окно намеренно **не расширяли**: при большем окне есть риск подтянуть прошлонедельный пост как текущий, что хуже пустоты.

### 4.7. Сводка прожига рапортовала «функция не упала» вместо «данные корректны» 🔴

**Системная проблема.** Семь зелёных галок при деке недельной давности — из-за этого проблему заметили только глазами на экране.

**Починка:** добавлены содержательные чеки — жёсткий ❌ на расхождение даты, ⚠️ на протухшие песни и видео, строка про слайд УМ с различением норм и ошибок.

### 4.8. Плеер фоновой музыки (побочка добавления слайда)

Добавление слайда разбудило латентный баг: рекурсия в `onCinemaSlideChanged` (`slidechanged → exitCinema() → Reveal.layout() → slidechanged → ∞`) давала `RangeError` и тормозила страницу. Петля существовала и раньше, но не срабатывала при старом наборе слайдов.

Починено флагом `_cinemaSyncing`. Попутно найдено:
- отсутствие `origin=<страница>` — без него JS-API-рукопожатие скрытого плеера не устанавливается, `playVideo()` — no-op;
- радио-миксы YouTube (`list=RD…&start_radio=1`) ненадёжно играют в iframe — теперь вычищаются;
- отсутствие `loop=1&playlist=ID` — фоновая музыка оборвалась бы после первого трека.

## 5. Ручное добавление новых Прабхат Самгитов через операторку

### Сценарий

Оператор хочет ввести новую ПС в каталог проекта. Порядок действий:

1. Открыть `/api/operator`.
2. В блоке «Песни» нажать «+ Добавить» без номера — откроется каталог. В каталоге нажать «+ Новая ПС».
3. Загрузить PNG/WEBP/JPG со слайдом ПС — превью появляется немедленно.
4. OCR запускается автоматически в браузере (браузерный Tesseract.js, без внешних запросов).
5. Через ~3–10 с поля «Номер», «Транслитерация» и «Перевод первой строки» заполняются автоматически.
6. Оператор проверяет результат. Поля, которые были отредактированы вручную до завершения OCR, не перезаписываются.
7. При необходимости — поправить вручную.
8. Нажать «Сохранить».
9. Запись появляется в каталоге (`song` в Postgres). Изображение кладётся в `dist/assets/songs/N.ext`.
10. Следующий билд manifest автоматически подхватит новую ПС.

### Архитектура

- **API:** `POST /api/song` (FastAPI, `server/main.py`) — принимает `number`, `title`, `translation`, `image` (multipart). Требует Basic-auth оператора.
- **Проверки при сохранении:** `number ≥ 1`, `title` непустой, расширение файла из `{webp, png, jpg, jpeg}`. Отказывает, если у числа уже есть изображение на диске **или** запись в таблице `song` — защита от случайной перезаписи.
- **Запись в БД:** `INSERT INTO song (number, title_translit, translation_first_line, stanzas, lang)`. `stanzas='[]'`, `lang='translit'` — заглушки; тексты стихов загружаются отдельно.
- **Dual-write:** изображение пишется в `deck/assets/songs/N.ext` **и** в `dist/assets/songs/N.ext` (если `dist/` существует). Без этого Caddy отдаёт файл, но после следующего `push.sh` файл оказывается только в одном месте.
- **Никакой параллельной системы.** Используется та же таблица `song` и те же поля, что и у изначального каталога (`songs_seed.json` → `seed_songs.py`). Нет нового механизма хранения, нет второй таблицы.

### OCR: браузерный Tesseract.js

**Принципиально браузерный.** VPS не делает внешних запросов — ни к внешним OCR-API, ни к CDN во время работы. Все ассеты самохостятся.

**Стек:**
- `tesseract.js@5` — главная библиотека (работает в странице)
- `tesseract.js-core@5` — WASM-движок Tesseract (работает в Web Worker)
- `rus.traineddata` + `eng.traineddata` (tessdata_fast) — модели

**Пути ассетов** (все под `/assets/ocr/`):

| Файл | Назначение |
|---|---|
| `tesseract.min.js` | основная библиотека, подключается тегом `<script>` |
| `worker.min.js` | воркер-скрипт, передаётся через `workerPath` |
| `tesseract-core-simd-lstm.wasm.js` | WASM-движок, автоматически выбирается браузером |
| `langs/rus.traineddata.gz` | русская модель (gzip, запрашивается браузером) |
| `langs/eng.traineddata.gz` | английская модель (gzip, запрашивается браузером) |

**Инициализация воркера:**

```javascript
Tesseract.createWorker('rus+eng', 1, {
  workerPath: '/assets/ocr/worker.min.js',
  corePath:   '/assets/ocr',      // директория → авто-выбор simd-lstm-варианта
  langPath:   '/assets/ocr/langs',
})
```

`corePath` — **директория**, не файл. Tesseract.js v5 сам выбирает `tesseract-core-simd-lstm.wasm.js` (если браузер поддерживает SIMD), иначе падает обратно на стандартный вариант.

**Важно про `.gz`:** Tesseract.js v5 запрашивает `rus.traineddata.gz`, а не `rus.traineddata`. Если `.gz`-вариант отсутствует → 404 → `initialization failed`. Скрипт `build/setup_ocr.sh` загружает `.traineddata` и сразу создаёт `.gz` рядом (`gzip -k -f`).

### OCR-алгоритм

**Единственный кроп:** верхние 25% изображения, полная ширина — `_cropCanvas(img, 0, 0, 1.0, 0.25)`.

Структура реальных слайдов: строка 0 — «Прабхат Самгит N» (или «ПС N»), строка 1 — опциональный заголовок песни заглавными буквами. Тело песни всегда смешивает транслитерацию CAPS + русские строчные на одной строке — это надёжный признак для разделения.

**Разбор результата:**

1. Текст кропа разбивается по строкам, каждая строка зачищается от диакритики.
2. **Номер** — `_ocrParseNumber(headerLines[0])`: ищет цифры после слова «Самгит», «ПС» и т.п.
3. **Заголовок** может быть на строке 0 как суффикс (`"ПС 6 - ПЕСНЯ ПРОБУЖДЕНИЯ"`) или на отдельной строке 1 (`"ПУРНОТБЕР ГИТО (ПЕСНЯ РЕАЛИЗАЦИИ)"`). Регэксп `[Пп]рабхат\s*[Сс]амгит\s*\d+\s*[-–—]?\s*(.+)` выделяет суффикс из строки 0.
4. Кандидат в заголовок проверяется `_isAllCaps`: порог 0.85 — ≥85% букв заглавные. Тело текста (смешанный регистр) через этот порог не проходит.
5. **Фильтр «ПЕСНЯ»:** если строка содержит «ПЕСНЯ» без скобок (`subtitleLine.toUpperCase().includes('ПЕСНЯ') && !subtitleLine.includes('(')`) — это жанровая метка (поле `subtitle` в БД), а не транслитерация. Пропускается, `upload-title` остаётся пустым.
6. Иначе — `_parseSubtitle`: формат `"TITLE (TRANSLATION)"` → `title=Пурнотбер гито`, `translation=Песня реализации`; без скобок → только `title`.

Семантика полей каталога (`songs_seed.json`):
- `title_translit` — транслитерация бенгальского названия кириллицей (например, «Э ган амар алор джхорона дхара»)
- `translation_first_line` — русский перевод первой строки тела
- `subtitle` — русская жанровая метка («Песня освобождения») — в форму загрузки **не входит**, ставится вручную при необходимости

**`\b` и кириллица:** в JavaScript `\b` работает только между `\w` и `\W`. Кириллица — это `\W` (не `\w`), поэтому граница между кириллическим словом и пробелом не является `\b`. Регэксп `/ПЕСНЯ\b/` на кириллице всегда возвращает false. Решение: `.toUpperCase().includes('ПЕСНЯ')`.

### Асинхронная защита

**Dirty-field protection.** `_ocrDirty: Set<string>` — множество идентификаторов полей, которые оператор отредактировал вручную. Функция `_ocrFill(fieldId, value)` проверяет `_ocrDirty` перед записью: если поле помечено грязным — OCR его не тронет, даже если закончится позже.

**Token-based race guard.** `_ocrToken: number` инкрементируется при каждом выборе файла. Стартовавший OCR сохраняет токен в замыкании и проверяет его после каждого `await`. Если токен сменился (оператор выбрал другой файл) — результат отбрасывается, blob-URL освобождается. Гонки состояний невозможны даже при быстрой смене файлов.

Воркер Tesseract.js создаётся один раз при первом запросе (`_ocrWorker`, ленивая инициализация) и переиспользуется для всех последующих распознаваний в одном сеансе страницы.

### Нестандартные слайды

**PS 29** (и подобные) — без стандартного заголовка «Прабхат Самгит N». Номер из OCR не извлекается. Все поля остаются пустыми. Оператор вводит номер вручную. Это правильное поведение: ложно-уверенные данные хуже пустых.

### Деплой ассетов OCR

`build/setup_ocr.sh` — запускается один раз на Mac перед первым деплоем с OCR:
1. Через npm загружает `tesseract.js@5` и `tesseract.js-core@5` во временную директорию.
2. Копирует JS/WASM файлы в `deck/assets/ocr/`.
3. Скачивает `rus.traineddata` и `eng.traineddata` (tessdata_fast) в `deck/assets/ocr/langs/`.
4. Создаёт `.gz`-копии каждого файла (`gzip -k -f`).

После этого обычный `build/push.sh` деплоит `deck/assets/ocr/` вместе с остальной статикой. На VPS файлы оказываются в `/opt/projects/dc-deck/dist/assets/ocr/` и отдаются Caddy.

## 6. Принципы, выработанные в процессе

Эти правила выведены из конкретных ошибок и стоит их соблюдать дальше.

**Единая точка LLM.** Один вызов на фичу, вокруг — детерминированный код. Сырой вывод модели не доходит до пользователя.

**Стоп-гейты между вехами.** Явное человеческое подтверждение перед переходом. Несколько раз это спасло от кодирования по неверной модели данных.

**Факт-чек перед кодом.** Не чинить по гипотезе. Дважды диагностика опровергала убедительную на вид версию (сначала «деплой не доезжает», потом «оверрайд блокирует песни»). Перед правкой парсера — проверить реальный каталог на предмет семантики полей. Перед деплоем — запустить тест на реальных изображениях.

**Один источник истины на сущность.** Корроборация «для надёжности» добавляет false-negative, а не надёжность. Airtable решает, есть ли КМ; пост УМ решает, каково расписание встречи.

**Триггер и классификация — одна функция.** Расхождение между «как красим» и «когда показываем» породило реальный баг.

**Whitelist, не blacklist.** Для rsync, для персистентных полей — везде, где забытый элемент приводит к тихой поломке.

**Сигналить, а не обнулять.** Экспирация уместна там, где есть автоматический источник замены (новости из Airtable). Где замены нет (песни) — пустой список опаснее устаревших данных: пустоту не заметят, неверные номера заметит любой поющий.

**Сбой источника не уничтожает живые данные.** Не нашли пост — сохранили прежнее + предупреждение.

**Различать ➖ и ❌.** Отсутствие опционального слайда — норма, а не ошибка. Иначе сводка будет врать про поломку каждую вторую неделю, и на неё перестанут смотреть.

**Не хардкодить то, что меняется.** Студия, учитель, формат встречи — из данных. Стабильные константы проекта — в конфиг-файл, не в код.

**Не строить впрок.** Ручной оверрайд расписания встречи не сделан, потому что плавающий формат постов — риск теоретический, а не наблюдённый. Вместо этого — дешёвая страховка от молчаливой деградации (⚠️ при `items ≤ 1`).

**Скоупить CSS.** Светлый слайд в тёмном деке требует изоляции под класс, проверенной рендером бок о бок.

**Лучше пусто, чем убедительно неверно.** Нестандартный слайд без надёжного источника номера → все поля пусты → оператор вводит вручную. Ложно-уверенный результат OCR хуже пустого поля.

**Проверять на реальных данных, не на симуляциях.** OCR прошёл три итерации диагностики (Python-симуляция → реальный Tesseract CLI → browser smoke-test), и каждый раз выявлял что-то, чего предыдущий слой не видел.

## 8. Бэклог

**Ближайшее:**

- **Адаптив под показ с телефона.** При подключении Pixel 9 через USB-C нужно сначала определить режим: desktop mode (независимый 16:9 — работ нет) или зеркалирование (портрет — нужны media-query, проверка фуллскрина на Android, wake lock от засыпания экрана, поведение скрытых YouTube-плееров на мобильном).
- **Шрифты и CSP.** Дек тянет Manrope с Google Fonts CDN, строгого CSP нет. На проде в РФ внешний CDN — точка отказа. Нужен самохостинг woff2 + `default-src 'self'`.
- **Структурный конфликт расписаний.** Пост ДЧ выходит ближе к выходным, прожиг идёт раньше — пост систематически не попадает в окно. Либо двигать прожиг, либо принять ручной ввод программы как штатный шаг.

**Известные края (задокументированы, не баги):**

- Если оператор сохранит форму до прихода номеров из чата, старые песни зафиксируются как «ручные на текущую неделю» и свежие не встанут автоматически.
- `parse_um_meeting` рассчитан на два наблюдённых формата постов; при дрейфе формата загорится ⚠️ (`items ≤ 1`), но парсер не самообучается.
- OCR не извлекает номер из слайдов без стандартного заголовка «Прабхат Самгит N» (например, PS 29) — это intentional, ручной ввод.
- `subtitle` (жанровая метка в БД) не заполняется через форму загрузки — только вручную через прямой SQL.
